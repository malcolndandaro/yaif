## Stack

Static HTML/CSS, single self-contained file at `docs/index.html`. No build step, no
framework, no JavaScript, and no local asset files: all texture and illustration is
generated in CSS and inline SVG, so the page is one file that opens from the filesystem
and from any static host.

One external dependency, deliberately accepted: the three typefaces (Archivo, Archivo
Black, Spline Sans Mono) load from Google Fonts. Self-hosting them would mean shipping
font binaries alongside the single file, which defeats the point of the format. The cost
is that offline, or behind a font-blocking proxy, the display voice falls back to the
platform sans. The fallback chain is therefore ordered to degrade to a real grotesk
(`Archivo Black → Archivo → Helvetica Neue → Helvetica → Arial`) and must **never**
include Impact or another condensed system display face.

**Publishing needs no build tooling.** The page lives at `docs/index.html` because `/docs`
on the default branch is one of GitHub Pages' two native branch-deploy sources (the other
being the repo root). Enabling it is a repo-settings change only — Settings → Pages →
Source: *Deploy from a branch* → `main` / `/docs`. No Actions workflow, no `gh-pages`
branch. `docs/.nojekyll` is present so Pages serves the directory verbatim instead of
running it through Jekyll.

Consequence: the page now sits **in the same directory as the seven markdown guides**, and
that is exactly why **every documentation link must stay an absolute GitHub blob URL**
(`https://github.com/malcolndandaro/yaif/blob/main/docs/…`). A relative link such as
`quickstart.md` would resolve on the published site and serve the file as **unrendered raw
markdown**, since Pages does not convert markdown with Jekyll disabled. Blob URLs render
properly on GitHub and work identically from the filesystem, from the published site, and
from a link pasted into Slack. Do not "simplify" them to relative paths.

## Users

Two audiences, one page — confirmed as co-primary:

1. **Customer data engineers** evaluating whether YAIF saves them months of work. They
   arrive with a concrete problem (often "we have hundreds of sources to land in the
   lakehouse") and want to see the shape of the code and the conventions before trusting it.
   They read like peers: skeptical of frameworks, allergic to indirection.
2. **Databricks field engineers (SAs/SEs)** looking for a reference architecture to reuse
   in their own accounts. They need to be able to drop the link in a customer channel and
   have it stand on its own.

Both are technical. Neither wants marketing language. The page is shared as a link, so it
must make sense with no verbal introduction.

## Product Purpose

YAIF (Yet Another Ingestion Framework) is a config-driven Databricks **Lakeflow** reference
for landing REST APIs, files, and SQL Server into Unity Catalog. One Asset Bundle,
consistent conventions, and a bronze → silver → gold medallion per source with AUTO CDC
SCD-1 dedup.

Success for the product: onboarding a new source is a **file copy plus a few field edits —
zero new framework code**. Success for *this page*: the visitor leaves having identified
which connector matches their source and clicked into that guide.

## Positioning

**An umbrella repo, not an abstraction layer.** Where Databricks already ships a
declarative primitive (Lakeflow Connect, SDP, Auto Loader), YAIF configures it rather than
wrapping it. Modules sit side by side sharing conventions — naming, medallion structure,
dev/prod targets, monitoring — but no code abstraction. There is no metadata engine.

This is the claim a neighboring project cannot truthfully copy, because most "ingestion
frameworks" are precisely the unified-metadata-layer anti-pattern YAIF was designed
against. The honest, self-aware name is part of the position.

The second half of the position: it scales by *generation*, not by hand-copying. The
motivating case is ~900 REST APIs — grouped into ~45 domains, driven from a control table,
with per-domain resources generated by a script.

## Operating Context

- Everything is driven from a Databricks Asset Bundle (`databricks.yml`) and the Databricks
  CLI: `bundle validate` → `bundle deploy -t dev` → `bundle run <job>`.
- One deployable unit per business domain: each `resources/<module>/<feed>.yml` is a
  self-contained schema + pipeline + job, giving failure isolation, independent schedules,
  and per-team grants.
- **Activate-by-moving**: feeds that need external infra (a UC `SQLSERVER` connection, a UC
  external location, real credentials) live in `examples/`, outside the deploy glob, and are
  activated by creating the prerequisite and moving the file into `resources/`.
- Shared medallion and job code lives in `src/` and is never copied per feed.
- Governed auth throughout: UC HTTP connections for APIs, UC connections for Lakeflow
  Connect, UC secret scopes for Basic-auth credentials. No secrets in code.
- Verification is SQL against the deployed schemas in any SQL warehouse.

## Capabilities and Constraints

Five modules, all built and verified end-to-end on a sandbox workspace:

| Module | Source | Mechanism |
|---|---|---|
| API | REST/HTTP APIs, one or hundreds | Governed UC HTTP fetch → SDP medallion; control-table driven; GET and POST/body |
| Files | Parquet/CSV/JSON in a bucket (incl. SAP via a connector) | Auto Loader (`cloudFiles`) over a UC Volume → SDP medallion |
| SQL Server — CDC | A SQL Server DB *with* CDC / Change Tracking | Lakeflow Connect: continuous gateway + ingestion; full change and delete history |
| SQL Server — query-based | A SQL Server DB *without* CDC/CT | Lakeflow Connect: scheduled cursor-driven pulls, no gateway |
| Oracle EPM (example) | `exportdataslice` (POST + Basic auth) | Customer-run template for POST/body/Basic-auth APIs |

Confirmed technical facts the page may state:

- **The transform pattern** is the default medallion idiom: named single-purpose
  `DataFrame -> DataFrame` functions in `src/shared/`, applied with `.transform()`. They
  touch no `spark.conf`, `dbutils`, or SDP decorator, so `tests/` covers them under a plain
  local SparkSession — no workspace, no deploy.
- **Two API silver shapes**: `records` (one row per record, keyed `(endpoint, record_id)`,
  converges to current state) and `document` (one VARIANT row per response, keyed
  `(endpoint, run_id)`, accumulates snapshot history).
- **AUTO CDC SCD Type 1** dedup to current state, keyed on the primary key; identical
  semantics across modules, only the sequencing column differs.
- **Query-based SQL Server requires a monotonic *modified* cursor column** that advances on
  INSERT *and* UPDATE. An identity/auto-increment PK as the cursor is insert-only and
  silently misses updates.
- **Lakeflow Connect SQL Server: ≤250 tables per ingestion pipeline** (documented Databricks
  recommendation). Beyond that, shard across multiple gateway-ingestion pairs.
- Verified demo counts exist and are real: content silver = 5,700; people silver = 210;
  files demo = 2 Parquet files / 100 rows through bronze/silver/gold.

Constraints:

- The repo is deliberately **customer-agnostic and scrubbed** of customer references, so the
  page must name no customer and must contain no workspace identifiers (hosts, IDs,
  warehouse IDs, IPs).
- Oracle EPM is **customer-run-only** — the repo ships placeholders and never calls
  `exportdataslice` from the author's sandbox. The page must not imply otherwise.
- Licensing, pricing, support commitments, and adoption numbers are **undecided/nonexistent**.

## Product Principles

1. **Configure the primitive, never wrap it.** If Databricks ships a declarative mechanism,
   YAIF's job is to configure it consistently — adding indirection is the failure mode.
2. **Onboarding a source is a file copy.** Any change that requires new framework code to
   add a source is a design regression.
3. **Scale by generation, not by hand-copying.** Past a handful of feeds, endpoints live in
   a control table and resources are generated.
4. **Governed by default.** Credentials live in Unity Catalog — connections and secret
   scopes — never in code, on every path.
5. **Honest about the boundaries.** Prerequisites, per-pipeline limits, customer-run-only
   templates, and known gotchas are stated plainly rather than smoothed over.

## Accessibility & Inclusion
