Five separations, one press

Each module is its own ink. They sit side by side sharing conventions (naming, medallion structure, dev and prod targets, monitoring) and share no code abstraction. Where the inks overprint is the only place anything is genuinely shared.

What the overprint actually is

with_ingest_stamps is imported by the API bronze layer and the files bronze layer. One definition, so the framework's ingest_date convention cannot drift between modules. That is the whole of the shared surface: plain DataFrame → DataFrame functions, no registry, no dispatch, no base classes.

  • The API module has real code, because raw REST fan-out needs it: threaded fetch, retries with backoff, a Delta landing table.
  • The SQL Server module is under sixty lines of actual configuration. Lakeflow Connect already is the connector; wrapping it would only add indirection.
  • The files module configures Auto Loader. The source genuinely is files in a bucket, which is what cloudFiles is for.

Bronze

The payload, untouched. Streaming ingest of the raw response or rows, append-only and audit-safe. For APIs that is the body as STRING plus a response_variant VARIANT; for files, the rows plus source-file lineage.

Silver

Parsed, checked, deduplicated. Quality expectations, then AUTO CDC SCD Type 1 keyed on the primary key. The latest row per key wins. Identical semantics across every module; only the sequencing column differs.

Gold

Whether it is actually working. Materialized views for monitoring: endpoint or ingestion health (success rate, errors, body size) and rows per day. Every domain gets them without writing them.

What the master looks like

Two things worth reading before you trust any of this: how the medallion code is written, and how little you have to type to see rows land.

The transform pattern · the default idiom src/transformations/silver_api_records.py 
@dp.temporary_view()
def silver_api_records_parsed():
    return (
        spark.readStream.table("bronze_api_responses")
        .transform(parse_json_records)      # body STRING -> _records array
        .transform(explode_records)         # _records -> one row per record
        .transform(project_record_columns)  # -> silver CDC source columns
    )

The step names replace a paragraph explaining what one thirty-line expression does. More usefully: these functions touch no spark.conf, dbutils, or SDP decorator, so tests/ runs them under a plain local SparkSession. No workspace, no deploy.

An umbrella repo, not an abstraction layer

Where Databricks already provides a declarative primitive, YAIF configures it and stops. There is no metadata engine and no wrapper around a managed connector. If you are tempted to build a unified ingestion metadata layer, don't. That is the anti-pattern this repo was designed against.

The thing it does replace is the bespoke notebook per source, which is precisely what does not scale to hundreds of sources.

Nine hundred endpoints, forty‑five masters

You never hand-build nine hundred jobs. The motivating case for this repo was a customer with roughly nine hundred REST APIs, and the answer is the one a print shop would give: cut a master per domain and run the drum.

  1. Group the endpoints into business domains: roughly forty-five, not nine hundred.
  2. Keep every endpoint in a control table, as a row: path, method, body, auth mode, silver shape.
  3. Run scripts/generate_api_domains.py. It writes one domain YAML per domain into a preview directory, never straight into resources/.
  4. Review the generated files, move the ones you want into resources/api/, and deploy.

Each domain YAML is a self-contained schema, pipeline, and job: about sixty lines. That is the unit of failure isolation, the unit of scheduling, and the unit of grants. Below a handful of domains, a file copy is genuinely faster than the generator.

Read the cautions before you run anything

These are the boundaries that actually bite. They are in the repo's own documentation too. None of them is a footnote.

  • The SQL Server gateway bills continuously

    A CDC gateway pipeline is continuous: true. Once deployed it runs, and bills, until you stop it. That is why it sits outside the deploy glob and has to be activated deliberately.

  • Query-based needs a real modified cursor

    The cursor column must advance on every INSERT and UPDATE: a ModifiedDate or rowversion. An identity primary key as the cursor is insert-only and will silently miss updates to existing rows.

  • 250 tables per ingestion pipeline

    Databricks recommends ingesting 250 or fewer tables per Lakeflow Connect ingestion pipeline. Beyond that, shard the table list across multiple gateway-and-ingestion pairs publishing into the same schema.

  • Oracle EPM is customer-run only

    The repo ships placeholders and never calls exportdataslice from the author's workspace, because that returns live planning data. For a runnable proof of the same POST, Basic auth, and VARIANT path, use the postman-echo demo instead.

  • Auto Loader cannot infer from an empty directory

    Point a files feed at a path that already holds at least one file, or expect the first update to no-op. This is also why API payloads land straight into a Delta table rather than through a volume.

  • Anything needing external setup is not in the glob

    A feed depending on a UC connection, an external location, or real credentials lives in examples/. You activate it by creating the prerequisite and moving the file, never by moving it first.
